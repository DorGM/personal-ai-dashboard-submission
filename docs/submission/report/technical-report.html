1. Executive summary

The Personal AI Dashboard is a local, private web application for analyzing one's own life: food and health, content consumption, job applications and tasks. It keeps deterministic history, statistics and charts, and adds an Analyst that answers natural-language questions only with what the records support. The runtime OpenAI agent may call six read-only, user-scoped tools; it never writes SQL and never writes numbers. The backend computes and renders every value, and a deterministic Evidence Validation layer (rules V1–V14) checks every claim before display. When the data cannot support an answer, the product shows a fixed, owner-specified message. A Demo Mode with a 30-day fictional dataset lets any reviewer run the product with no Google account and no API key.

The project was also an exercise in disciplined AI-assisted engineering: every design decision was proposed by a Claude Code Architect agent and approved by the owner, and every implementation task was closed only after an independent Verifier agent passed it. Verifiers rejected work more than ten times; each rejection exposed a defect that the implementing agent's own green test suite had missed (§7).

2. Problem and objectives

People who log their sleep, meals, workouts, reading or job search usually end up with scattered records and no trustworthy way to ask "what actually changed?". General chat assistants answer fluently, but they invent numbers, ignore gaps in the data and imply causation. The product goal is the opposite: a personal analyst that may only say what the records support.

Intended experience

  • Record daily activities through accessible forms on desktop or phone; duplicates are rejected with a clear message.
  • Review a 15-day history per domain where an undocumented day shows a placeholder (in Hebrew, per the original specification) and is never a zero.
  • See trends in aggregates whose denominators are documented days only.
  • Ask a question and get a validated answer with coverage and evidence, a partial answer naming what is missing, or an honest "not enough data".

Domain rules that shape the AI design

RuleConsequence for AI
Missing ≠ zero; denominators are documented daysThe agent cannot turn "forgot to log" into "did nothing".
Database uniqueness is authoritative; no automatic overwriteNo model output can replace a stored record.
Retrieval and arithmetic are fixed, parameterized SQLNo model-generated SQL; user scoping cannot be bypassed by prompt text.

Scope evolution

The first approved scope (Phase A, 16 Oct) also contained external intelligence: job-recommendation and industry-trend agents using web search, and AI free-text intake. Two recorded owner decisions narrowed it. ADR-005 (17–18 Oct) refocused the product on analyzing the user's own data, described by the owner as a deliberate conceptual shift; LOG-019 then deferred AI free-text intake so that runtime AI is concentrated on analytics. Superseded text was kept and marked, never deleted.

3.1 Analytics architecture

ADR-005 separates what the model decides (which tools to call, how to phrase findings) from what the backend guarantees (every number, coverage statement, direction and caveat).

  • Closed metric registry shared with the dashboard (e.g. sleep.hours, steps.count, tasks.completion_rate), each with kind, unit and a minimum meaningful change.
  • Six tools with strict argument models (extra="forbid", so the model cannot pass a user_id); the user comes only from the server-side session. Queries are module-level constants chosen by enum, values bound with ?; a static test bans string-built SQL.
  • Hardened read-only connection: query_only, a deny-by-default authorizer, a 2-second statement budget, row caps, 8 KB result trimming. In Demo Mode the Analyst opens only the active demo working copy and fails closed otherwise.
  • Evidence ledger and placeholders. Each tool result becomes an evidence item (E1…E8) with a SHA-256. The model writes "Average sleep was {{E3.b.mean}}" and cites E3; the backend substitutes formatted values and appends coverage lines and an "association only" caveat.
RulesRequirementDeterministic check (default thresholds)
V1–V2Well-formed and supportedStrict schema; every finding cites existing evidence; every placeholder resolves to an allowed field of cited evidence.
V3No free numbersNo digit or English number word outside placeholders.
V4–V5Enough dataValue ≥ 3 observations; trend ≥ 7 points over ≥ 14 days at ≥ 50% coverage; correlation ≥ 10 pairs; groups ≥ 5 days.
V6–V7Missing days; comparable periodsCoverage line always shown; absolute words rejected when coverage < 1; comparisons need ≥ 3 documented days and ≥ 40% coverage per period.
V8–V9Correct values and directionDerived fields recomputed; stated direction must match the backend sign; below the minimum change it must read "no clear change".
V10No causationRejects causal and predictive wording ("because", "leads to", "will", …).
V11–V14Consistency and safetyFinding kind matches the tool; no URLs or markup; status consistent; charts only from compatible evidence.

On failure the model gets one repair turn containing only error codes. If it fails again, invalid findings are dropped (status partial) or, if none remain, the owner's fallback text is shown. Unvalidated model text is never displayed. The OpenAI client sits behind an injected ModelClient port (Responses API, store=false, 30 s per call, 75 s per question, a 40,000-token budget, 20 questions per hour, one in flight) with privacy-safe logging.

4. Claude Code methodology

Owner (human)Product direction, approvals, corrections, external accounts.Approval is never inferred from silence.

These build-time Claude agents are distinct from the runtime OpenAI agent inside the product. Their definitions are committed in .claude/agents/, and CLAUDE.md states the workflow every session follows.

Human gates

Phase A ran on 16 Oct: scope, stack, schema, AI sources and security, then UI and test matrix, each approved, amended or corrected by the owner before GATE-A authorized implementation. Later material changes (the data-preservation policy, the product refocus, soft delete, the 30-day dataset, the public release) each have a recorded owner decision. Paid API use, dataset approval and publication were never decided by an agent.

Source-of-truth discipline

PROJECT_PLAN.md holds task state with Completed / Not completed / Verification / Evidence fields; DEVELOPMENT_LOG.md records prompts, decisions, defects and observed results; a resume checkpoint let new sessions continue without conversational memory. Unverified claims stay labelled as such.

Parallel workstreams

From LOG-019 the work ran in three isolated checkouts under a written protocol (docs/architecture/parallel-work-and-metrics-contract.md):

WorkstreamScopeRule
Integration LeadDemo Mode → metrics → dashboard → integrationOnly writer to main and the planning documents
Analytics workerTools, validator, agent, Analyst UIBuilt against a frozen metrics contract and an in-memory fake until the registry merged
Submission workerReport draft, audit, release procedureDocumentation only

Exclusive file ownership made merges clean; the cost was that analytics tools were verified against a fake until integration, which is why an integration Verifier ran on the merged result.

5. Prompts and iterations

Appendix B presents ten curated interactions, selected for engineering value rather than volume. Each states the challenge, the original prompt (quoted verbatim from the recorded session where available, and labelled), what the AI produced, the owner's judgment, the iteration and verification that followed, and the takeaway. The full sanitized entries are in docs/submission/prompts/. Recurring patterns:

  • Prompts as contracts. The most effective prompts stated acceptance criteria and prohibitions ("Wait for my explicit approval", "Do not merge B-15 until the isolation fix passes verification") rather than implementation steps.
  • Human correction of plausible AI framing. The Architect presented AI calorie re-estimation as an acceptable exception to "AI never edits a saved record"; the owner rejected the framing and the design became append-only before any code existed.
  • Agents checking agents. The main session verified an Architect claim against git history and found it false; Verifiers repeatedly rejected green Coder work.
  • Honest status under time pressure. Release requests asked for "exact blockers" and "do not represent unfinished work as complete"; the release notes therefore list what was not run.

6.3 Scripted-model tests and the live evaluation plan

Validated with a scripted modelNot validated without a live model
  • Tool arguments are schema-checked; a model-supplied user_id is rejected.
  • Turn, call, token and time limits stop the loop.
  • Every number shown comes from the backend; invented numbers, causal words and undocumented-day claims never reach the page.
  • One repair turn, then partial or fallback, exactly as specified.
  • Record text with injection strings never reaches the answer.
  • Only the signed-in user's data, and in Demo Mode only the demo copy, is read.
  • Whether a real model picks the right tools and periods.
  • How often it follows the placeholder protocol, and so how often answers degrade to partial or fallback.
  • Readability and usefulness of real answers.
  • Latency, token use and cost per question.
  • Compatibility of the request with the live API beyond its tested shape.

Live evaluation plan (requires the owner's approval and a key with a hard budget): run the golden set and the adversarial set against one pinned model with store=false on the demo fixture; record per question the status (answered, partial, fallback), validator rejections and repairs, evidence recall against the reference calculator, latency and tokens; report the model name and date; label every result as live; never let a live result replace an offline assertion.

9. Critical reflection and risks

What worked

  • Independent verification paid for itself. F-01 needed six rounds; each FAIL exposed a bypass that a self-reviewed green suite would have shipped.
  • Recorded human gates caught a design misframing before any code and kept scope changes explicit.
  • Moving trust from the model to the backend (placeholders instead of numbers, fixed tools instead of SQL) made AI correctness testable with ordinary deterministic tests.
  • A frozen interface contract let analytics proceed in parallel with the metric registry.

What I would do differently

  • Test forms through their own rendered fields from the start, and verify guards by behaviour, not by text.
  • Run the suite on the reviewer's platform early: the Windows line-ending defect was invisible on Linux.
  • Budget the golden set and a small, approved live run before the release window, so the AI claims rest on measured model behaviour, not only on the guarantees around it.
  • Commit the Verifiers' browser journeys as an E2E suite instead of keeping them as per-task probes.

Tradeoffs accepted

ChoiceCost
One agent + deterministic validator (no RAG, no multi-agent)Questions limited to what six tools express; single-turn only.
Heuristic thresholds (V5–V9)Not significance tests; may refuse borderline real effects.
English lexical rulesBest effort; idioms can slip through, although rendered numbers always carry the true sign.
Server-rendered UI without JavaScriptSimple and CSP-friendly, less interactive.
Parallel workstreamsIntegration risk concentrated at the end.

Remaining risks and limitations

  • Real-model behaviour, answer quality and cost are unmeasured (§6.3).
  • "Steps on aerobic days" is not expressible (no tool filter), and a comparison with zero events in one period falls back; both are open design questions.
  • Single-user local app; a copied session cookie stays valid until its 8-hour expiry; rate limits are per process.
  • Windows fixes and PowerShell scripts not re-run on Windows; no screen-reader or contrast audit.
  • The synthetic dataset is not yet owner-approved; some invented organization names may resemble real ones.

10. Conclusion

The project delivers a small, working, reproducible product whose AI component is constrained so that its correctness can be checked by ordinary deterministic tests: the model chooses tools and words, the backend owns every number and every claim. The development process shows the same principle applied to the AI tools that built it: Claude Code agents proposed, implemented and verified, but approvals came from the owner, and each task was closed only on independent evidence. The main open item is equally clear: the live behaviour of the runtime model has not been measured, and the report says so rather than implying otherwise.

02. Calorie re-estimation: correcting an "exception" into an append-only design

Phase A / A-03 schema (edge case E2) · Date: 2026-10-16, 10:58–11:15 UTC · Verbatim excerpt of a recorded prompt

Challenge. The project rule was that the runtime AI never overwrites saved records. The owner also wanted meal calories to be re-estimated whenever a meal changes. The Architect resolved the tension the wrong way, and the error had to be caught before any schema was built.

approve A, but E2 needed to be treated more deeply - i want the LLM to calculate the calorie each time a meal is added, edited or deleted on fly, which means that the LLM gets the prompt, extract items, and if it found a meal within the prompt, it calculate the calories and it will be added to the relevant field. […]

Human judgment. The owner rejected the "exception" framing. A rule that admits a convenient exception stops being a rule. The owner restated the requirement as additive: every change creates a new record, and the daily total is derived. The owner then chose "Estimates table" (11:15 UTC). Main Claude logged the misframing as its own error: "I also logged that the "exception" wording was my mistake, which you caught."

Takeaway. Explaining a requirement as an "exception" was a sign that the model had not yet found a design that satisfied the rule. An append-only data model satisfied both constraints at once, and it also produced an audit trail. Full entry.

03. Data-integrity directive: ADR-004 and six Verifier rounds

Phase B / F-01 foundational safeguards (inserted before B-02) · Date: 2026-10-17, 18:45–19:54 UTC · Verbatim excerpt of a recorded prompt

Challenge. A read-only schema review had found residual risks (L1–L4), including one where INSERT OR REPLACE could silently delete a user's data. The owner made data preservation a project-wide requirement: no automatic deletion during sign-in, updates or migrations, and safe migrations under real concurrency.

1. Data Integrity and Deletion Policy — Highest Priority Data preservation must be a fundamental architectural requirement throughout the entire project. * No automatic or unintended deletion of user data is allowed during authentication, updates, synchronization, migrations, or error handling. […] * Prevent destructive SQL operations, including unsafe INSERT OR REPLACE patterns. […] Do not implement new deletion features […]

Human judgment. The owner set the policy and the execution order and approved routine decisions within scope. Main Claude adopted some defaults without escalating them and recorded each one (LOG-011):

  • RESTRICT plus grant-guarded deletes;
  • the soft-delete design deferred to B-04 for owner approval;
  • frontend URL validation deferred until forms exist.
