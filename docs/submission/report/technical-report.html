Appendix A. Decision register

1. Executive summary

The Personal AI Dashboard is a local, private web application for analyzing one's own life: food and health, content consumption, job applications and tasks. It provides deterministic history, statistics and charts, and an Analyst that answers natural-language questions with answers grounded in the user's records. A runtime OpenAI agent may only call six read-only, user-scoped tools; it never writes SQL and never writes numbers. Every value shown is computed by the backend, and every claim passes a deterministic Evidence Validation layer (rules V1–V14) before display. When the data cannot support an answer, the product says so in a fixed, Owner-specified message.

A Demo Mode with an entirely synthetic 30-day dataset lets any reviewer install and explore the product with no Google account and no API key.

2. Problem definition and intended user experience

People who log their sleep, meals, workouts, reading or job search usually end up with scattered records and no trustworthy way to ask "what actually changed?". General chat assistants can produce fluent answers, but they will happily invent numbers, ignore gaps in the data, and imply causation. The product goal is the opposite: a personal analyst that is only allowed to say what the records support.

Intended experience

  • Record daily activities quickly through accessible forms on desktop or phone; duplicates are rejected with a clear message.
  • Review a 15-day history per domain where an undocumented day shows "No record entered for this day" (in Hebrew in the UI) and is never treated as a zero; every value shows its actual record date.
  • See trends in aggregates whose denominators are documented days only (e.g. 7 workouts on 5 documented days = 1.4 per day).
  • Ask a free-form question ("Did my sleep improve in the second half of the month?") and get either a validated answer with coverage lines and evidence, a partial answer that names what is missing, or an honest "not enough data".

Domain rules that shape everything else

RuleWhy it matters for AI
Missing ≠ zero; denominators = documented daysThe agent cannot turn "forgot to log" into "did nothing".
Database uniqueness is authoritative; no automatic overwriteNo model output can ever replace a stored record.
All retrieval and arithmetic is fixed, parameterized SQLNo model-generated SQL; user scoping cannot be bypassed by prompt text.

3. Initial architectural approach and iterative product adaptation

The project ran in two controlled stages (§7). In Phase A (16 Oct 2026, 13:47–14:23) the Architect proposed one bounded decision at a time and the Owner approved, amended or corrected each: MVP scope (A-01), stack (A-02), schema (A-03), AI sources and auth (A-04), UI and test matrix (A-05), then GATE-A authorized implementation.

The original scope included external intelligence: a job-recommendation agent and an industry-trend agent using OpenAI web search, triggered by a "Run now" button (max 3/day), plus AI free-text intake with a clarification loop.

Adaptation 1 — focus on the user's own data (ADR-005)

After the foundation was in place, the Owner issued a directive (recorded verbatim in owner-directive-2026-10-17-personal-ai-analytics.md) to concentrate the product on analyzing the user's own life, activities, habits and trends. The directive states that this is a deliberate conceptual shift and not a token, cost or time decision. External job discovery, recommendations and trend retrieval moved out of the MVP (tables kept, no UI); a single grounded analytics agent, Evidence Validation and Demo Mode moved in. The change was handled as a planning-only session: the Architect wrote ADR-005 with a supersession table and twelve open decisions (O-0…O-12), Main Claude corrected one Architect claim against git history (LOG-016), and nothing was implemented until the Owner approved the decisions (LOG-017).

Adaptation 2 — concentrate runtime AI on analytics (LOG-019)

The Owner then deferred AI free-text intake (B-06): "Manual data entry from B-04 is sufficient for this submission," so that the product's runtime AI is concentrated on personal analytics and evidence-grounded insights. The same directive set the dataset to about 30 fictional days and introduced a controlled parallel workstream for analytics (§7.3).

Both adaptations narrowed the surface where an LLM can be wrong, and moved it to the place where the backend can check it.

6. Analytics architecture

The analytics design (ADR-005 §3–§5) separates what the model decides (which tools to call, how to phrase findings) from what the backend guarantees (every number, coverage, direction and caveat).

6.1 Metric registry and read-only tools

  • Closed registry (B-05, shared with the dashboard): e.g. sleep.hours, steps.count, weight.kg, workouts.count, tasks.completion_rate, job_applications.progress_rate, each with kind, unit and min_delta.
  • Six tools with strict Pydantic argument models (extra="forbid", so no user_id can be passed). user_id comes only from the server-built ToolContext.
  • Fixed SQL only: module-level constant queries chosen by enum; values bound with ?; a static test bans string-formatted SQL in app/analytics/.
  • Hardened read-only connection: PRAGMA query_only, a deny-by-default authorizer, a 2 s statement budget, row caps, and 8 KB result trimming.

6.2 Evidence ledger and placeholder rendering

Each successful tool call becomes an evidence item (E1…E8) with normalized arguments and a SHA-256 of its result. The model writes prose such as "Average sleep was {{E3.b.mean}} in the second half" and cites E3. The backend replaces placeholders with formatted values (hours to 1 dp, steps with separators, signed deltas, DD.MM.YYYY dates), appends a coverage line ("Based on N documented days of M") and, for relationships, the caveat "Association only; this does not show cause." Text stored by the user (untrusted_text) can never be addressed by a placeholder.

6.3 Deterministic validation (V1–V14)

RuleRequirementCheck (default thresholds)
V1–V2Well-formed, supportedStrict schema; every finding cites existing evidence; every placeholder resolves to an allowed leaf of cited evidence.
V3No free numbersNo digit or English number word outside placeholders.
V4–V5Data exists, enough of itValue ≥ 3 observations; trend ≥ 7 points over ≥ 14 days at ≥ 50 % coverage; correlation ≥ 10 pairs; groups ≥ 5 days.
V6–V7Missing days, comparable periodsCoverage line always shown; absolute words and "skipped/missed" claims rejected when coverage < 1; comparisons need ≥ 3 documented days and coverage ≥ 0.4 per period.
V8–V9Values and direction correctDerived fields recomputed (tolerance 1e-9); declared direction must match the backend sign; below min_delta it must be "no clear change".
V10No causationRejects causal and predictive language ("because", "leads to", "improves", "will", …).
V11–V14Consistency and safetyFinding kind matches tool; no URLs or markup; status consistent; charts only from compatible evidence.

If validation fails, the model gets one repair turn containing only error codes. If it still fails, invalid findings are dropped (status becomes partial) or, if none remain, the Owner's fallback is shown: "The available records do not provide sufficient reliable information to analyze {topic} for the selected period. You can add relevant records or expand the date range and try again." Unvalidated model text is never displayed.

6.4 OpenAI integration

Designed (B-15): Responses API with function calling via an injected ModelClient port, store=false, 30 s per call and 75 s per question, a per-question token budget (default 40,000) and an hourly cap (default 20, one in flight), privacy-safe logging (never the question, results or output). Tests replace the client with scripted models. NOT RUN No live OpenAI call has been made; live evaluation requires the Owner's O-9 approval.

Threats and controls

ThreatControl

Repository audit (submission session, 18 Oct)

Tree and full history of 9 commits scanned (docs/submission/security-pii-audit-report.md). No live credential, personal email, real record, CV, database, log or screenshot was found. Two history-level items prevent publishing the private history as is: a company name in the first commit (removed from the files later at the Owner's request), and private session links in every commit message. The public repository will therefore be a fresh single-commit snapshot of a verified release (public-release-procedure.md); the private history is preserved unchanged.

Reproducibility and deployment

  • Clean clone → venv → pip install -e ".[dev]" → scripts\start.ps1 -Demo; no credentials required.
  • Fixture checksum and generator --check make the demo data reproducible; the working copy is rebuilt on every start or reset.
  • The app is a local process; it does not need to stay hosted. After a demo the server and any tunnel are stopped and the API key is revoked.

14. Critical reflection, tradeoffs, limitations and future work

What worked

  • Independent verification paid for itself. F-01 needed six rounds; each FAIL exposed a bypass that a self-reviewed green suite would have shipped.
  • Recorded human gates caught a design misframing (LOG-005) before any code and kept scope changes explicit rather than drifting.
  • Moving trust from the model to the backend — placeholders instead of numbers, fixed tools instead of SQL — made AI correctness testable with ordinary deterministic tests.
  • A frozen contract allowed analytics to progress in parallel with the metric registry.

What we would do differently

  • Test forms through their own rendered fields from the start (B-04 D-1), and verify guards by behavior, not by text (F-01).
  • Run the suite on the reviewer's platform early: the Windows line-ending defect (W-1) was invisible on Linux and would have blocked the reviewer's first step.

Tradeoffs accepted

ChoiceCost
Single agent + deterministic validator (no RAG, no multi-agent)Questions limited to what six tools can express; single-turn only.
Heuristic thresholds (V5–V9)Not significance tests; may refuse borderline but real effects.
English lexical rules (V3, V6, V9, V10)Best-effort; idioms and negations can slip through, although rendered numbers always show the true sign.
Server-rendered UI without JSSimpler and CSP-friendly, but less interactive.
Parallel workstreamsIntegration risk concentrated at the end; tools verified against a fake until B-05 merges.

Known limitations

  • Single-user local application; offline when the process stops. A copied session cookie stays valid until its 8 h expiry.
  • Demo dates shift with the anchor, so there are no weekday patterns.
  • On Windows, until the line-ending fix lands, a default clone breaks the demo fixture checksum (W-1, §11); two tests depend on the locale or on symlink privileges (W-2, W-3).
  • No real Google sign-in, live OpenAI, tunnel, screen-reader or contrast checks yet.

Future improvements

  • Committed Playwright E2E suite in CI; accessibility audit with measured contrast.
  • Opt-in live evaluation harness with labelled results and cost reporting.
  • Multi-turn analyst conversations with per-turn re-validation; localization of lexical rules.
  • Re-introduce AI free-text intake under the same insert-only, validated-repository guarantees.
