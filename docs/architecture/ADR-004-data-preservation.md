# ADR-004 — Data preservation and deletion policy

**Status:** Accepted 2026-10-17 (directed by the project owner; supersedes A-03 E11 "hard delete; ON DELETE CASCADE").
**Scope:** database schema, migrations, repositories, authentication and every later write path.

## Policy (owner's requirement)
1. No automatic or unintended deletion of user data — not during sign-in, updates, sync, migrations or error handling.
2. User data is deleted only after an explicit, authorized action by that user; the UI shows a confirmation dialog explaining consequences; the backend independently validates authorization and intent.
3. Prefer recoverable soft deletion where appropriate; permanent deletion is a separate, clearly distinguished action.
4. Deletions are atomic and never touch unrelated rows; integrity and FK consistency are checked afterwards.

## Decisions
| # | Safeguard | Mechanism | Why |
|---|---|---|---|
| D1 | No cascading deletes | Every FK is `ON DELETE RESTRICT`. | Deleting (or REPLACE-ing) a parent can never silently remove children; the L2 scenario (REPLACE on `users` wiping all data) becomes impossible. |
| D2 | Deletes need a grant | `deletion_grants(table_name, row_id)` + a `BEFORE DELETE` trigger on every user-owned table and `users`. A delete succeeds only if a grant exists for that row (or, for owned child rows, for its parent). `app/deletion.py` is the only code that writes grants: inside one transaction it checks ownership, then within one savepoint grants, deletes children then parent, and revokes. The table is therefore empty at rest: migrations must leave it empty with its exact definition, and startup refuses a database holding standing grants. | Intent is enforced by the database, not by convention; a stray `DELETE` raises. |
| D3 | REPLACE cannot delete; guards can't be switched off | Connections from `app.db.connect` (the only place that opens SQLite connections, enforced by a static test) set `PRAGMA recursive_triggers = ON`, so the implicit delete performed by `INSERT OR REPLACE`/`REPLACE INTO` fires D2's trigger and aborts. An SQLite authorizer on those connections refuses all schema changes (`CREATE`/`DROP` of tables, indexes, views and triggers including temporary triggers, `ALTER`, `ATTACH`/`DETACH`) and changing `foreign_keys`, `recursive_triggers`, `writable_schema`, `ignore_check_constraints`, `defer_foreign_keys`, `journal_mode`, `synchronous` or `locking_mode`; only the migration runner may change the schema (temporary tables/views for queries stay allowed). A static test rejects `OR REPLACE`, `OR IGNORE`, `REPLACE INTO`, `ON CONFLICT REPLACE/IGNORE` and `ON CONFLICT … DO UPDATE` in `app/`, `scripts/` and `migrations/`. | Defense in depth for L2. |
| D4 | Stable identity | `BEFORE UPDATE` triggers (no column list, so updates via `rowid`/`_rowid_`/`oid` are caught) abort any change to `id`, `user_id` or parent links; `users.google_sub` is immutable. Edits are targeted `UPDATE … WHERE id = ? AND user_id = ?` of named columns only. | Editing a record can't re-home or renumber it or touch unrelated rows. |
| D5 | Sign-in never rewrites users | First sign-in is `INSERT … ON CONFLICT (google_sub) DO NOTHING` followed by a `SELECT` (never REPLACE or DO UPDATE). Profile fields (email, display_name) may be updated by a targeted `UPDATE`; `id` and `google_sub` never change. | Repeated or concurrent sign-ins keep the same `users.id` and all related rows. |
| D6 | Migrations preserve data and guards | Runner executes statement by statement inside one `BEGIN IMMEDIATE` transaction. Transaction control, `PRAGMA` and `ATTACH`/`DETACH` are rejected by keyword before anything runs and by an SQLite authorizer while statements run. Temporary objects are refused during migrations. Before `COMMIT` it rolls back if any pre-existing table lost rows, if `schema_migrations` was touched, or if an invariant breaks: every table registered in `app/guards.py` has its guard triggers **exactly** as generated by `guard_triggers()` (so a guard can't be dropped, weakened or mistyped); no other trigger references `deletion_grants`; any table with a `user_id` column or a foreign key to a registered table must itself be registered, with `user_id` referencing `users(id)` (directly or through a composite parent key); no foreign key cascades or sets null; nothing uses REPLACE/IGNORE conflict resolution. Then `integrity_check` and `foreign_key_check`. | A migration can restructure tables but cannot lose rows, drop the guards, or half-apply. |
| D7 | Job-run slots stay permanent | `job_reports` rows are deletable only with a grant for their **user** (future account deletion), so Run-now slots can't be freed (A-03 E8). | Keeps the 3/day cap honest. |

## Deferred (decided when the feature is built, with owner approval)
- **Soft delete (B-04):** which tables get `deleted_at`, how uniqueness treats soft-deleted rows (partial unique indexes), restore and purge UX.
- **Confirmation dialogs (B-07)** and **account deletion** (not in MVP scope).

## Consequences
- 001_init.sql was amended in place (no database had been deployed or committed); later schema changes must be new migration files.
- Tests may only delete through `app.deletion`; direct `DELETE` in tests is expected to fail.

## Known limits
- **Migrations are trusted, reviewed code.** D6 detects lost rows and missing or altered guards at COMMIT, not changed contents: while it runs, a migration could drop a guard, renumber ids or delete-and-reinsert rows, then restore the guard. Any migration that changes data or ids needs explicit review.
- **Indexes on `deletion_grants`** are not checked; at worst they make sanctioned deletion fail (fails safe). An extra `BEFORE DELETE … RAISE(IGNORE)` trigger would make deletes silent no-ops (no data lost).
- **Parent-table rebuilds.** Tables referenced by others (`users`, `meals`, `job_reports`) can't be rebuilt with create-copy-drop-rename, because `RESTRICT` is enforced immediately and switching `foreign_keys` off is forbidden. If one is ever needed, the runner must gain a reviewed procedure first (architect decision). `ADD COLUMN` and child-table rebuilds that re-create the guard triggers work.
- **New user-owned tables** must be added to the `GUARDED` registry in `app/guards.py` and create the triggers that `guard_triggers()` returns; otherwise the migration is refused.
- **Raw connections.** Code that opens SQLite directly (outside `app.db.connect`) would bypass D3. Only `app/db.py` may call `sqlite3.connect`; a static test enforces this for `app/` and `scripts/`. External tools (e.g. a SQLite browser) are outside these guarantees.

**Related (planned, ADR-005):** a `read_only=True` mode of `app.db.connect` for the analytics tools (query_only plus a SELECT-only authorizer), and guarded cleanup of disposable synthetic Demo Mode working copies under `data/demo/`. Neither changes the rules above.
